| Incremental ingestion | Not started | Skip re-extracting and re-embedding files that haven't changed, instead of a full rebuild on every `prepare_corpus.py` / `ingest_documents.py` run. Today, `index_manager.py::ingest()` always does `reset=True` (full Chroma collection delete + recreate) and always deletes and rebuilds the BM25 pickle from scratch; `document_register.py`'s `content_hash` is only used to catch duplicate files within one run, not to detect unchanged files across runs. Design already sketched in [`THE_JOURNEY_TO_PRODUCTION.md`](THE_JOURNEY_TO_PRODUCTION.md#1-raw-storage-and-change-detection) — Stage 1: content-hash registry (a DB row per source file) plus LlamaIndex's `IngestionPipeline` + docstore-backed upsert-by-hash, the direct upgrade from the current full-rebuild `ingest()`. Cited in `docs/ARCHITECTURE_ASSESSMENT.md` as one reason for the deliberate 4/10 production-readiness score.<br><br>**Intended approach — use LlamaIndex's own incremental primitives rather than hand-rolling change detection:** `llama_index.core.ingestion.IngestionPipeline`, constructed with a `docstore` (`SimpleDocumentStore` for a local-first fit, matching this project's no-external-infra approach — confirmed against the installed package: `IngestionPipeline.__init__` takes `docstore`, `vector_store`, and `docstore_strategy` directly) and `docstore_strategy=DocstoreStrategy.UPSERTS_AND_DELETE` (confirmed available on the installed `llama-index-core`, alongside `UPSERTS` and `DUPLICATES_ONLY`) — `UPSERTS_AND_DELETE` upserts changed/new documents *and* removes nodes for documents no longer present in the input set, which is the same "deleted source records cannot leave stale vectors" guarantee `ingest()`'s current full-rebuild docstring cites as the reason it's full-rebuild today, just delivered incrementally instead. BM25 has no equivalent incremental primitive in `llama-index-retrievers-bm25` (`BM25Retriever.from_defaults()` builds fresh from an in-memory node list every time) — likely stays a cheap full rebuild from whatever nodes the docstore reports as current, since embedding calls (not BM25 indexing) are the expensive part this is meant to avoid paying twice. Not yet verified: exact `SimpleDocumentStore` local persistence path/format, and whether `IngestionPipeline.run()` handles vector-store insertion itself or still needs a separate `VectorStoreIndex` step — confirm both before implementing. |
