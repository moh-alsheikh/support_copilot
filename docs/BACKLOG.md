| Incremental ingestion | Done (2026-11-10) | **Built:** `index_manager.ingest()` now runs LlamaIndex's `IngestionPipeline` with a `SimpleDocumentStore` persisted to `storage/ingestion_pipeline/docstore.json` and `DocstoreStrategy.UPSERTS_AND_DELETE`; BM25 is rebuilt from every node read back from Chroma; full rebuilds happen on request (`--full-rebuild` / `--force`), with no docstore to diff against, or when `vector_policy()` changes. Both open questions resolved from the source: the pipeline writes to the vector store itself, and `store_doc_text` must stay on because `UPSERTS_AND_DELETE` deletes via `docstore.delete_document()`, which raises for text-less entries. **Verified:** 7 tests in `tests/test_incremental_ingestion.py`; on the sample knowledge base an unchanged re-run went from 270 s (full) to 4.8 s with 0 nodes embedded, and hybrid retrieval metrics were identical. Extraction (`prepare_corpus.py`) still reprocesses every file.<br><br>**Original entry:** Skip re-extracting and re-embedding files that haven't changed, instead of a full rebuild on every `prepare_corpus.py` / `ingest_documents.py` run. Today, `index_manager.py::ingest()` always does `reset=True` (full Chroma collection delete + recreate) and always deletes and rebuilds the BM25 pickle from scratch; `document_register.py`'s `content_hash` is only used to catch duplicate files within one run, not to detect unchanged files across runs. Design already sketched in [`THE_JOURNEY_TO_PRODUCTION.md`](THE_JOURNEY_TO_PRODUCTION.md#1-raw-storage-and-change-detection) — Stage 1: content-hash registry (a DB row per source file) plus LlamaIndex's `IngestionPipeline` + docstore-backed upsert-by-hash, the direct upgrade from the current full-rebuild `ingest()`. Cited in `docs/ARCHITECTURE_ASSESSMENT.md` as one reason for the deliberate 4/10 production-readiness score.<br><br>**Intended approach — use LlamaIndex's own incremental primitives rather than hand-rolling change detection:** `llama_index.core.ingestion.IngestionPipeline`, constructed with a `docstore` (`SimpleDocumentStore` for a local-first fit, matching this project's no-external-infra approach — confirmed against the installed package: `IngestionPipeline.__init__` takes `docstore`, `vector_store`, and `docstore_strategy` directly) and `docstore_strategy=DocstoreStrategy.UPSERTS_AND_DELETE` (confirmed available on the installed `llama-index-core`, alongside `UPSERTS` and `DUPLICATES_ONLY`) — `UPSERTS_AND_DELETE` upserts changed/new documents *and* removes nodes for documents no longer present in the input set, which is the same "deleted source records cannot leave stale vectors" guarantee `ingest()`'s current full-rebuild docstring cites as the reason it's full-rebuild today, just delivered incrementally instead. BM25 has no equivalent incremental primitive in `llama-index-retrievers-bm25` (`BM25Retriever.from_defaults()` builds fresh from an in-memory node list every time) — likely stays a cheap full rebuild from whatever nodes the docstore reports as current, since embedding calls (not BM25 indexing) are the expensive part this is meant to avoid paying twice. Not yet verified: exact `SimpleDocumentStore` local persistence path/format, and whether `IngestionPipeline.run()` handles vector-store insertion itself or still needs a separate `VectorStoreIndex` step — confirm both before implementing. |

Semantic search ranks Q001's row 43rd because a bi-encoder blurs the digits that identify it. Possibly also fewer `llama3.2:3b` false refusals from cleaner evidence (hypothesis; needs the answer evaluation).<br><br>**Intended approach — LlamaIndex's built-in `SentenceTransformerRerank`** (`llama_index/core/postprocessor/sbert_rerank.py`, confirmed in the installed `llama-index-core`), with three required overrides: pass a **relevance-trained** model (MS MARCO MiniLM-class to start; the default `cross-encoder/stsb-distilroberta-base` is a sentence-*similarity* model), set `trust_remote_code=False` (default is `True`), and keep `semantic_rank`/`bm25_rank` in node metadata. New dependencies: `sentence-transformers` and PyTorch (not installed today) plus a model download; check first whether Ollama can serve a reranker instead. Keep tests offline with an injectable scorer.<br><br>**Done when:** Q001 and Q007 reach the top 4 in hybrid mode, context precision rises, no question's rank gets worse across all 23, and added latency is measured on this CPU (estimate ~1–2 s per question for a MiniLM-class model). Then update the hybrid row in `learning/vector-similarity-scoring.md` (scores change scale) and re-score §3 in `RAG_TECHNIQUE_COVERAGE.md`. |
| Stable node IDs | Done (with incremental ingestion) | `SentenceSplitter` gave every chunk a random UUID, so an unchanged corpus got new chunk IDs (shown in citations) and a new `corpus_sha256` on every build, and incremental upserts couldn't line chunks up. `ingestion/parsers.py` now passes `id_func=chunk_id`, deriving each ID from the document's stable ID plus the chunk's position (`<doc_id>:<n>`). Covered by `test_requested_full_rebuild_keeps_node_ids_and_fingerprint_stable`. |

| Keep metadata out of embedded and BM25 text | Not started | Each chunk's metadata (`content_hash`, `encoding`, `doc_id`, `extraction_method`, …) is embedded and BM25-indexed alongside its text. Since BM25 policy 2 counts one-character tokens, metadata digits such as line numbers and the `8` in `utf-8-sig` are searchable too. Fix by setting `excluded_embed_metadata_keys` / `excluded_llm_metadata_keys` on documents in `ingestion/document_adapter.py` (keep `source`, `title`, `location` if they help retrieval), then measure retrieval before and after. Changes document hashes, so incremental ingestion re-embeds everything once. |

Needed before any further model comparison. |
